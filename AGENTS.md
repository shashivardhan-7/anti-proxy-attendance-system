# AntiProxy Attendance System

## Project Goal

Build a polished university anti-proxy attendance MVP based on a three-layer security architecture:

1. Rotating QR verification
2. BLE proximity verification
3. Biometric + device binding

The system must feel like a real production product, not a student CRUD application.

## Applications

### Mobile

React Native + Expo + TypeScript.

One mobile application with two roles:

* Professor
* Student

### Dashboard

Next.js + TypeScript + Tailwind CSS.

### Backend

FastAPI + Python.

### Database

Supabase PostgreSQL.

## Core Attendance Flow

Professor:

1. Login
2. Select/create class
3. Start attendance session
4. Display rotating QR
5. Broadcast BLE session identifier
6. Monitor live attendance

Student:

1. Login
2. Biometric authentication
3. Scan live QR
4. Detect professor BLE signal
5. Submit attendance
6. Receive verification result

Backend:

1. Validate session
2. Validate QR token
3. Validate timestamp
4. Validate single-use rules
5. Validate student
6. Validate device
7. Validate BLE evidence
8. Record attendance
9. Record security events

## Security Requirements

QR tokens must:

* expire rapidly
* contain session identity
* contain timestamp
* contain nonce
* be cryptographically verifiable
* prevent replay

Attendance must never be directly written by the client.

All attendance submissions must pass through the backend.

## MVP Principle

Prioritize working demonstrations over unnecessary complexity.

The following must be genuinely functional:

* rotating QR
* QR expiry
* biometric authentication
* BLE detection
* backend attendance validation
* live dashboard updates
* security event logging

Advanced production security can initially be represented by a clean abstraction and strengthened later.

Do not fake security functionality while presenting it as implemented.

## UI Requirements

The UI must look like a polished commercial security product.

Avoid:

* default Expo styling
* generic Bootstrap dashboards
* excessive gradients
* unnecessary animations
* clutter

Prefer:

* dark security-oriented visual language
* excellent typography
* clean cards
* clear status indicators
* subtle animations
* responsive layouts
* strong empty/loading/error states

## Demo Requirements

The final demonstration must support these scenarios:

1. Successful attendance
2. Expired QR rejection
3. BLE proximity failure
4. Unregistered device rejection
5. Duplicate attendance rejection

The admin dashboard must show security events generated by failed attempts.

## Development Rules

Before changing architecture, inspect the existing implementation.

Do not rewrite working code unnecessarily.

Do not introduce dependencies without a reason.

Use TypeScript strictly.

Use environment variables for secrets.

Never commit secrets.

Write reusable components.

Keep security-sensitive validation on the backend.

When implementing a feature:

1. inspect existing code
2. plan the change
3. implement
4. test
5. fix errors
6. summarize changed files

Do not create fake APIs when a real backend endpoint is expected.

## AI Coding Rules

Cursor should act as a senior engineer.

Do not blindly generate large amounts of code.

Prefer small, testable changes.

When an error occurs, diagnose the root cause instead of applying random fixes.

Never remove functionality simply to make an error disappear.

Preserve the architecture unless there is a clear technical reason to change it.
